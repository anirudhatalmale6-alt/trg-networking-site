TASK 1 - TWO PHP EXTENSIONS  (5 minutes, do this first, nothing depends on it)
--------------------------------------------------------------------------

GD and fileinfo are not enabled. Without GD, WordPress cannot resize an
uploaded photo, so a 4 MB image straight off a phone is served at full size to
every visitor and pages become very slow. Without fileinfo, WordPress has to
guess at file types from their names.

In C:\PHP\php.ini, uncomment:

       extension=php_gd2.dll
       extension=php_fileinfo.dll

Restart the PHP FastCGI application pool afterwards.

To confirm: I can verify both from my side once it is done. Just say when.

ALREADY DONE - the upload limit. The 5 September version of this note also
asked you to raise upload_max_filesize from 2 MB. That turned out not to need
you: both it and post_max_size are PHP_INI_PERDIR settings, so a .user.ini in
the site's document root sets them without touching php.ini and without a
restart. I have put one there:

       upload_max_filesize = 32M
       post_max_size = 40M          (must stay above the upload limit - the
                                     POST body is the file plus the form
                                     fields around it)
       memory_limit = 256M
       max_execution_time = 300
       max_input_time = 300

Verified in place with ini_get_all() and then proved properly by pushing a
3.8 MB PDF through the dashboard's own upload form. Nothing for you to do, but
worth knowing the file is there: if you later set different values in php.ini,
the .user.ini will still win for this site. web.config already refuses to serve
it over the web.

One quirk if you ever edit it: PHP caches .user.ini per FastCGI worker for five
minutes, each worker from the time of its own first request. So for a few
minutes after a change, consecutive requests report the old and new values in
turn. It is not broken; wait five minutes before concluding anything.

TASK 2 - BIND THE SSL CERTIFICATE
--------------------------------------------------------------------------

TRG already owns a certificate. It needs to be a .pfx file (the certificate
together with its private key) plus the password for that file.

Do not send the .pfx or its password to me or through the Freelancer chat.
It should not travel. Import it directly on the server.

a) Import the .pfx into the Local Computer certificate store, Personal folder.

b) In IIS Manager, select the site whose path is
   D:\inetpub\trgnetworking.com, open Bindings, and add:

       Type https, port 443, hostname trgnetworking.com,     this certificate
       Type https, port 443, hostname www.trgnetworking.com, this certificate
       Type http,  port 80,  hostname trgnetworking.com
       Type http,  port 80,  hostname www.trgnetworking.com

   Keep the existing test.trgnetworking.com bindings. Do not remove them.

c) Please check first whether the certificate covers both trgnetworking.com and
   www.trgnetworking.com. Most do. If it is a wildcard (*.trgnetworking.com) it
   will also cover test.trgnetworking.com - in that case please add an https
   binding for test.trgnetworking.com as well.

   That last point is worth the extra minute. It would let me test the entire
   site over https and prove it works BEFORE any DNS is touched, instead of
   finding a certificate problem after the domain has already moved.

   Right now https on the test address returns 404, because there is no
   binding of any kind on port 443.

TASK 3 - DNS  (do not do this until tasks 1 and 2 are finished)
--------------------------------------------------------------------------

Nameservers are ns1/ns2/ns3.trgnetworking.com, so this is controlled in-house.

WHAT CHANGES - exactly two records:

       trgnetworking.com        A       ->  20.124.224.234
                                            (currently 52.35.104.127)

       www.trgnetworking.com            ->  20.124.224.234
                                            (currently a CNAME to
                                             host.axionthemes.com)

WHAT MUST NOT CHANGE - please read this part carefully:

       MX      trgnetworking-com.mail.protection.outlook.com
       TXT     v=spf1 ip4:50.76.20.81 include:md02.com ... -all
       TXT     MS=7BBCCAC7DB29955143A359598E7217C857B78883
       TXT     google-site-verification=XHRYJY1cnNHNSWenR4SQo0XmoyfW6FxqNAbHByWpo-g
       TXT     _dmarc  v=DMARC1; p=quarantine; adkim=s; aspf=s;
       plus the two DKIM selector records

Those are Microsoft 365. If the zone is rebuilt from a default template rather
than edited, company email stops - and it is not obvious for a day or two,
because outbound mail keeps working while inbound quietly fails.

One piece of good news, since I checked the record rather than assuming: the
SPF record does NOT contain an "a" mechanism. Some do, and where they do,
repointing the A record silently authorises the web server to send mail as the
domain. TRG's SPF lists specific IP addresses and specific services instead, so
this move cannot cause that problem. Just leave the record alone.

TIMING:

- The day before: lower the TTL on those two records to 300 seconds. This is
  what makes the switch reversible in five minutes instead of a day.
- After the switch: leave the old axionthemes site running for a week. It costs
  nothing and gives us somewhere to fall back to.

TASK 4 - MICROSOFT 365 MAILBOX  (independent of everything above)
--------------------------------------------------------------------------

The website's enquiry form saves every message to the database, but it cannot
send notification email yet.

The server is on Azure, which blocks outbound port 25 entirely. I measured this
from the machine itself: ports 25, 587 and 465 to the Microsoft 365 mail host
are all blocked, while smtp.office365.com on port 587 is open. So authenticated
submission through Microsoft 365 is the only route available. That is not a
preference, it is the only thing the network permits.

Needed:

a) Enable SMTP AUTH on the mailbox that will send (it is off by default in
   Microsoft 365 tenants).
b) Create an app password for that mailbox.
c) Give the app password to Dr. Edwards, who will paste it into the website's
   own Email settings screen.

Do not send the password to me. The website has a settings page for it
precisely so that nobody has to.
